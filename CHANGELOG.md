# Changelog

All notable changes to this project. Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
versioning follows [Semantic Versioning](https://semver.org/):

* **0.x.y** – beta. **1.0.0** is the first version considered complete.
* **x.Y.0** – new features (new registers, new options).
* **x.y.Z** – bug fixes, documentation, tests.
* Changes that could alter an entity ID (key renamed/removed, platform changed, unique ID scheme changed) are
  **breaking changes**. They are marked in bold here and need a migration path.

## [Unreleased]

## [0.14.0] – 2026-11-08

### Fixed
- **No more "value changed outside Home Assistant" notice for the circulation pump.** The controller may switch it
  itself (time schedule, hot water run), so a change is no evidence of another Modbus client. Other writable
  settings are reported as before. The pump stays an ordinary switch and is still never restored after a reset.

### Added
- **Ready-made dashboards** (`dashboards/`, English and German, profiles *basic* and *full*, plus an optional view
  with the HACS card apexcharts-card): overview, energy, locks and grid, control, diagnostics and an automation
  view. Built-in cards only; entity IDs are predicted or, with `tools/gen_dashboard.py --registry ...`, looked up in
  your entity registry. See `docs/dashboard.md`. The visual rendering in a browser was not checked.
  Pump (HUP, BUP, ZIP) tiles in the overview, outputs in the diagnostics view and, if enabled, the EVU input levels
  in the locks and grid view with a note that the EVU polarity is inferred from one measured state.
  Written for 0.13.0: one *Firmware version* tile, "COP (10 min)", status sensors as text.
- **Three blueprints** (`blueprints/automation/luxtronik_shi/`): block while a signal is on, trigger with
  hysteresis, notify about problems. They select entities with an integration filter.

### Tests
- `tests/test_dashboard.py` (generated files up to date, structure, predicted entity IDs equal the IDs Home
  Assistant creates, in English and German) and `tests/test_blueprints.py` (validation and behaviour against the
  simulated heat pump).

## [0.13.0] – 2026-11-07

### Added
- **Binary sensors for the pumps, outputs and EVU inputs.** New keys on registers the firmware analysis proves:
  `pump_heating` (HUP, 10354), `pump_hot_water` (BUP, 10355), `pump_circulation` (ZIP, 10356), `output_vbo` (10350)
  and `output_fp1` (10351) are enabled; `output_fp2`, `output_fp3` (not measured, no such circuit on the reference
  installation), `input_evu` (10360) and `input_evu2` (10361) are disabled by default. They read the registers of the
  matching `raw_<address>` sensors, which keep their keys and stay disabled; a register shared by both is read once.
  For the EVU inputs only the name is proven; that level 1 means "released" is inferred from one measured state, so
  they are named "level" and show the level, not "locked" (the operating mode *utility lockout* reports the lock).
  Entries from before 0.3.0 (no equipment option) do not get them, as with earlier additions.
- `icons.json` (icon translations: operating mode and status per state, error number, firmware, COP, pumps, outputs
  and inputs), generated by `tools/gen_icons.py`.
- Devices that the configured equipment no longer has (cooling or pool switched off) can be deleted in Home
  Assistant; the main device and devices with entities cannot.
- Diagnostics: a `polling` section with the interval, the duration of the last poll, polls, failed polls, failures
  in a row, time of the last success and failure, the last error and the registers that are not polled. No
  additional Modbus reads.
- Descriptions for host, port, unit ID and name in the setup and reconfigure dialogs.
- README: section *Energy dashboard* (the energy counters are `total_increasing` kWh values).

### Changed
- **Registers of disabled entities are no longer polled.** A register is read only if its entity is enabled, or the
  integration uses it itself (firmware version, the control values compared after an outage, every key the restore
  and the reset detection use, the setpoint modes and effective targets, the inputs of the COP sensors, the
  equipment flags and the sources of the climate, water heater and status bit entities). Enabling an entity reads
  its register at once and adds it to the following polls; disabling removes it. Default installation, simulator
  request plan: 35 blocks and 16.5 requests per poll on average before, 28 blocks and 14.2 after (all equipment
  selected, new binary sensors included).
- **One failed poll no longer makes every entity unavailable.** A poll that fails once (a network glitch, a busy
  controller) keeps the previous values for that cycle; entities become unavailable only when the next poll fails
  as well. Nothing else changes: the failed poll still starts the outage clock of the *Smart Home Interface not
  reachable* issue (after 10 minutes), and the next successful poll counts as recovery for the restore and the
  change notices exactly as before. A first poll that fails at setup is still retried by Home Assistant.
  The tolerance is `POLL_FAILURES_TOLERATED` in `const.py` (1; 0 restores the old behaviour).
- Every platform now declares `PARALLEL_UPDATES` (read-only `binary_sensor` and `sensor`: no limit; `switch`,
  `number`, `select`, `climate`, `water_heater`: one write at a time). No visible change: the Modbus client already
  serialised all access to the SHI.
- The suggested name of a new heat pump follows the language of Home Assistant ("Wärmepumpe" for German, otherwise
  "Heat pump") instead of always being German. Existing entries and entity IDs are untouched.
- `switching_lock_minutes`, `min_runtime_minutes` and `dhw_min` (fixed firmware constants 20, 20 and 300, SHI
  analysis) are disabled by default for new installations and documented as constants. Existing registry entries
  keep their state.

### Tests
- `tests/test_poll_plan.py`, `tests/test_output_flags.py`, `tests/test_icons.py`, `tests/test_poll_tolerance.py`,
  `tests/test_parallel_updates.py`; the other outage tests run with the tolerance switched off
  (`tests/conftest.py`), because they count every failed poll.

## [0.12.0] – 2026-11-07

### Action required
- **The three firmware entities are gone** (owner-approved exception to the entity contract): `fw_platform`,
  `fw_major` and `fw_minor` ("Firmware: platform / major version / minor version"). They are replaced by one
  diagnostic sensor, `firmware_version` ("Firmware version", e.g. `3.92.3`). The integration deletes the old registry
  entries at the next start. Remove them from dashboards and automations; nothing else uses them.
- **The COP sensor is now a 10 minute value** (key and entity ID unchanged, name "COP (10 min)"). It is unknown
  for the first minutes of a compressor run and 10 minutes after it stopped, instead of showing single readings. Check
  automations that expect a value at every moment.
- **The status sensors (heating, hot water, cooling, pool) report text** instead of 0 to 3: `disabled`, `no_request`,
  `requested`, `running` (shown translated). Automations and templates that compare with numbers must use these
  keys. A value outside 0 to 3 is `unknown_<n>` ("Unknown (<n>)").

### Changed
- **COP over a time window.** The old per-reading quotient (thermal power / electric power) showed spikes of 6 to 10
  right after a compressor start (history of 2026-11-06/07: 8.0, 6.3, 9.3, 10.3), jumped between neighbouring ratios
  of whole numbers (4.32 / 4.37, both powers have a resolution of 100 W) and was unknown whenever the electric power
  was below 200 W. The COP is now the energy ratio of the last 10 minutes (integral of thermal power / integral of
  electric power, from the samples already polled; no extra Modbus reads). It is unknown while the window holds less
  than 60 Wh of electric energy (compressor stopped, or the first 2 to 4 minutes of a run, where the thermal power
  register still ramps up) and when the result is not between 0 and 12. Gaps of more than 150 s (failed polls) and
  missing values are not interpolated. Defrost inside a run counts: negative thermal power lowers the COP, as it
  does in reality. The limits are design choices of this integration, not register facts. COP overall (energy
  counters) is unchanged.
- **Status of heating, hot water, cooling and pool as text.** Values from python-luxtronik `ModeStatus`
  (inputs 10003, 10004, 10006, 10007; range 0 to 3): 0 disabled, 1 no request, 2 requested, 3 running. German and
  English texts.
- **Water heater operations have short, capitalised labels**: *No influence / Keine Vorgabe*, *Setpoint / Sollwert*,
  *Offset / Anhebung*, *Level / Stufe* (the mode selects keep their long explanations). Keys and values are
  unchanged. The labels were added in 0.10.0 together with the rename of `off`; an installation still on 0.9 or older
  shows the raw keys.

### Fixed
- **The firmware version was read in the wrong order.** Registers 10400, 10401 and 10402 are major, minor and patch
  (python-luxtronik `version`; the reference installation reads 3 / 92 / 3). The code treated 10401 and 10402 as
  major and minor, so the device showed "92.3 (Plattform 3)" and the *firmware outdated* repair issue could never
  appear. The device now shows `3.92.3` and the issue compares major and minor correctly.

### Documentation
- **Entity reference** ([docs/entities.md](docs/entities.md), German: [docs/entities.de.md](docs/entities.de.md)):
  every entity sorted by topic with key, unit, value range, meaning and pitfalls, plus short background on heat
  pumps (heating curve, hysteresis, buffer tank, COP and JAZ, defrost, Legionella protection). The page is generated
  by `tools/gen_entity_docs.py` from the register map, the platforms and the translations, so the list cannot go
  stale; the prose is in `tools/entity_docs_texts.py` and `tools/entity_docs_entries.py`. Linked from both READMEs.

### Tests
- `tests/test_cop.py`: the window (steady state, start spike, minimum energy, 100 W resolution, idle, gap, missing
  value, defrost, upper limit) and the entity over simulated time.
- `tests/test_entity_polish.py`: status texts including unknown values and translations, the single firmware entity,
  removal of the old registry entries, firmware issue order, water heater labels, no `off` operation.
- `tests/test_entity_docs.py`: both pages match the generator, every key of the entity contract is documented, every
  entity has an explanation and no explanation belongs to an unknown key.
- `tests/test_parallel_updates.py`.

## [0.10.1] – 2026-11-07

### Fixed
- **Hot water settings are no longer reported as failed when the controller takes them with a delay.** Firmware
  3.92.3 commits SHI writes to the hot water group (10005–10008) about 10 s later, and writing the current value
  cancels such a pending write (see *Deferred writes of the hot water group* in the firmware analysis; measured for
  10005, while 10006 read back at once). A differing read-back of these registers is now checked once more after
  15 s, with one extra read of that register, and nothing is written to it meanwhile. Applies to writes through Home
  Assistant and to restores.
- **The restore after a device reset retries instead of forgetting.** After the reboot on the reference installation
  on 2026-11-07 the hot water mode and setpoint were not restored and forgotten. A restore value that does not read
  back is now kept for 10 minutes and retried on later polls (once per poll, at most 5 attempts). Hot water group
  values wait while the hot water block reads on (owner measurement: the hot water mode can only be set while the
  block is not active; mechanism unknown). A circuit's mode is still written last, after its values succeeded. Only
  after the deadline or the attempts run out is a value forgotten, with the existing warning; a write through Home
  Assistant cancels the retry.

### Tests
- `tests/test_deferred_writes.py`: the fake SHI models the pending map with its delay, the cancel rule and the block
  refusal. Covered: a late commit is no failure and is confirmed after 15 s, a repeated write while pending is not
  sent, a restore with a deferred commit, a reboot with the hot water block on (restored after the release), the
  deadline, and a user write cancelling the pending restore.

## [0.9.0] – 2026-11-07

### Action required
- **Update intervals longer than 5 minutes are reduced to 5 minutes (300 s).** The SHI drops every value set over it
  after 10 minutes without Modbus access, even with the restore option off, so the options now allow 10–300 s. An
  existing entry with a longer interval polls every 300 s and logs a warning; its stored option is kept until you save
  the options once.
- **Write ranges of nine settings now follow the python-luxtronik source (`holdings.py`), with the owner's approval.**
  The Home Assistant number, climate and water heater entities (and so the limits an optimizer reads from them)
  change as follows. Check automations and optimizers that rely on the old limits.

  | Key | Address | Old range | New range |
  |---|---|---|---|
  | `cfg_heating_setpoint` (also the climate entity) | 10001 | 10–70 °C | 15–75 °C |
  | `cfg_heating_offset` | 10002 | −5 … +5 K | −20 … +20 K |
  | `cfg_dhw_setpoint` (also the water heater entity) | 10006 | 10–65 °C | 30–75 °C |
  | `cfg_dhw_offset` | 10007 | −10 … +10 K | −20 … +20 K |
  | `cfg_mk1_setpoint` | 10011 | 10–70 °C | 20–65 °C |
  | `cfg_mk1_offset` | 10012 | −10 … +10 K | −5 … +5 K |
  | `cfg_mk1_cool_setpoint` | 10016 | 5–40 °C | 5–25 °C |
  | `cfg_mk1_cool_offset` | 10017 | −10 … +10 K | −5 … +5 K |
  | `cfg_overall_offset` | 10066 | −10 … +10 K | −20 … +20 K |

  Ranges got wider for the heating and hot water settings and the overall offset, and narrower for mixing circuit 1
  (setpoint, offset, cooling setpoint and offset). Values outside the new range are rejected before anything is
  written. Keys and unique IDs are unchanged.
- **Three keys of already released entities were renamed (with the owner's approval): `raw_10109` is now
  `outside_temp_average`, `raw_10110` is now `heat_source_input` and `raw_10112` is now `max_flow_temp`.** Your entities are kept: on start the integration moves
  the registry entries to the new unique IDs, so entity IDs, history, customised names, areas and the enabled/disabled
  state stay as they are. Only the name is new for 10110 and 10112 (*Temperature: heat source inlet*, *Temperature:
  flow maximum*; 10109 keeps *Temperature: outside average*) and the unique ID ends with the new key. Check
  automations, templates or tools that look entities up by the old unique ID `<entry_id>_raw_10109` /
  `<entry_id>_raw_10110` / `<entry_id>_raw_10112`; entity IDs are unaffected.
- `max_flow_temp` (10112) is now a temperature in °C (0.1 °C resolution, uint16, from python-luxtronik) instead of a
  unitless raw number. If you had enabled it, the value changes from e.g. `600` to `60.0`, and Home Assistant starts
  long-term statistics for it.
- **The options of the five level selects now follow the python-luxtronik `LevelMode` source.** `cfg_heating_level`
  (10003), `cfg_dhw_level` (10008), `cfg_mk1_level` (10013), the mixing-circuit-2/3 levels and `cfg_overall_level`
  (10067) previously offered `evu_lock`/`reduced`/`normal`/`boost` (raw 0/1/2/3); they now offer
  `normal`/`increased`/`increased2`/`decreased` (raw 0/1/2/3). So the value written for a given selection changes
  (e.g. `normal` wrote 2 before and writes 0 now). Keys and unique IDs are unchanged. Check automations or optimizers
  that set or read a level option.

### Added
- **Restore after a device reset** (option, off by default, so existing installations behave as before). The SHI drops
  every value set over Modbus when the controller reboots or its watchdog expires (see *SHI watchdog* in
  `docs/firmware-3.92.3-shi-analysis.md`); measured on the reference installation (LWDV 91-1/3, FW 3.92.3), heating
  mode (10000) read `off` instead of `setpoint` after two reboots and heating level (10003) raw 0 instead of 2.
  - Only an allow-list is remembered and restored (`RESTORE_KEYS` in `const.py`): mode, level, offset and setpoint of
    each circuit and the room setpoint. Blocks, circulation, extra hot water, the power limit and the overall group
    (`cfg_overall_*`, 10065–10067, semantics unproven) are never remembered, adopted or restored.
  - **Info notice when base values change:** if a confirmed reset relearns a setpoint's reset value, one information
    notice (a persistent notification, not a repair issue, in English or German) lists the changed base values
    (before -> now) and the restored values, and says that no action is needed. A later relearn replaces it.
  - Only values written through the integration's own entities and read back unchanged are remembered (persisted per
    entry, so it survives a restart); values set back to neutral are remembered as such. Values written by other
    Modbus clients or over port 8889 are not remembered.
  - **A reset is only considered after an outage**: failed polls, a re-established Modbus connection (counted in the
    client, so a reboot shorter than the poll interval is not missed), or a gap of more than 660 s since the last
    successful poll. Any change seen while polling continuously is an external change and is forgotten.
  - **All or nothing**: after an outage it is a reset only if every remembered value reads its reset value (0 for
    modes, levels and offsets; for setpoints any non-zero value, or exactly the learned value). Then the differing
    values are restored, values first and modes last; otherwise the changed values are forgotten and nothing is
    restored. A single remembered mode reading 0 after an outage is enough.
  - **Learned setpoint reset values**: after a confirmed reset the value each setpoint reverted to is stored; later a
    setpoint only counts as reverted if it reads exactly that value. Learned on the device, not a firmware table.
  - **Adopts the current device values once when the option is switched on** (options flow or first setup): every
    allow-listed mode, level and offset that reads non-zero, and a setpoint only if its circuit's mode is
    `setpoint` (an unset setpoint reads its boot default). Logged; not repeated on restart or reload.
  - Adopted values may have been set by another client and are restored like the integration's own. Who set a value
    cannot be read over Modbus, so an adopted setpoint can also be a boot default or a controller parameter; after a
    reset in which that parameter changed it is written back over the change, and the SHI then owns it.
  - The in-session gap is measured with a monotonic clock.
  - The reconnect signal rests on an **assumption not yet measured** on the reference installation: the SHI keeps the
    TCP connection open between polls. If reconnects happen on 3 of the last 5 polls, reconnects stop counting as an
    outage for the session (warning once). More than 600 s since the previous successful poll also counts as an
    outage.
  - A setpoint that blocks a reset only because it differs from its learned value is named in a warning; after a
    reboot with failed polls and every remembered mode and level at 0 the reset is accepted and the learned value
    replaced. `0x7FFF` is never a reset value or learned. A remembered register that becomes unavailable is
    forgotten. Learned values are kept regardless of age; turning the option off and on clears them.
  - Diagnostics list the learned values, the reconnect count, the time of the last reconnect and whether reconnects
    still count as an outage.
  - Group rule: once a member of a circuit changed externally, the circuit's mode is forgotten until it is written
    through Home Assistant again. A mode is not restored if another value of its circuit failed to restore.
  - Restores run with read-back, once per reset; failures are not retried; no second restore within 15 minutes;
    remembered values older than 24 hours are dropped; Home Assistant writes and restores are serialised by a lock.
  - Diagnostics list the remembered values. No extra polling, no new entities.
  - **Changed since #45 (not released yet):** two zeros without an outage are no longer a reset (they are external
    changes); after an outage a partial revert restores nothing instead of the zeros; a single remembered mode or
    level reading 0 after an outage is now restored (it used to need two remembered values); a reconnect without a
    failed poll now counts as an outage; setpoint reset values are learned.
- Binary sensors for the status bits of heat generator state (10000): `heatpump_vd2_status`, `heatpump_zwe2_status`
  and `heatpump_zwe3_status`, from python-luxtronik (bit 1, bit 3 and bit 4). All three are disabled by default.
  `heatpump_vd2_status` and `heatpump_zwe2_status` show the same bits as `compressor_2` and `aux_heater_2`.
- Undocumented raw values, all disabled by default and polled every 30th cycle: inputs 10352, 10353, 10410–10413, 10416,
  10417 and 10500–10502 (`unknown_input_*` in python-luxtronik), as `raw_<address>`. Their meaning is unknown, so they
  stay raw values. Entries created before 0.3.0 (no equipment option) do not get them, so their polling load stays the same.
- `cfg_room_setpoint` (holding 10060): writable room-temperature setpoint of the room control unit (number,
  20–40 °C, 0.5 °C step; only with the *room unit* equipment option). Firmware V3.92.3 exposes this address as the
  writable `RBE_RoomTemperatureSetpointRegister` (target `RBE_RT_Soll`); see
  `docs/firmware-3.92.3-shi-analysis.md`. 10060 was never released as a raw value, so there is no migration.

  selects expose the python-luxtronik order (`normal`/`increased`/`increased2`/`decreased`).

- README (English and German): notes on the renamed keys and on the added raw values.
- New `docs/firmware-3.92.3-shi-analysis.md`: an independent decompilation of the controller firmware V3.92.3
  that verifies the register map (signs, scaling model, writability, operating-mode set, fixed constants)

  facts" rule. It also records open points for later decisions: the `_LEVELS` option order disagrees with

  It is removed when the values match the pre-outage values again or when dismissed. The pre-outage values are kept
  in memory only and are lost on a Home Assistant restart. No new registers, no extra Modbus reads, no entity
  changes. Texts are generated by `tools/gen_translations.py`.

  only to users who enable "Show beta versions". Stable releases are unchanged.

  or power cut (volatile SHI holding registers). The integration does not detect or correct this (issue #9).

## [0.7.0] – 2026-11-05

### Added
- Repair issue (issue #24), shown under Settings > System > Repairs and deleted automatically when the condition ends
  (also when the entry is unloaded): *SHI not reachable* (error), raised when all polls failed for 10 minutes in a row.
  The issue ID contains the config entry ID, so several heat pumps do not clash. No new registers, no extra Modbus
  reads, no entity changes. Texts are generated by `tools/gen_translations.py`.
- Calculated COP sensors (issue #23), no new registers and no extra Modbus reads: `cop` (thermal power 10300 / electric
  power 10301, in the main heat pump device) and `cop_heating` / `cop_dhw` (thermal / electric energy counters of
  heating and hot water, 10322/10312 and 10324/10314, in the *Heating* / *Hot water* device). A sensor is unknown
  (never a number) when an input is missing, the electric value is zero or below the minimum (200 W / 1 kWh), the
  thermal value is zero or negative (e.g. defrost), the result is above 12, or an energy counter went backwards since
  the previous reading. These limits are a design choice, not register facts.
- Water heater entity for domestic hot water (issue #20), in the *Hot water* device. Target temperature writes the
  existing hot water setpoint register (10006, 10 ... 65 °C in 0.5 K steps, out-of-range values are rejected before
  anything is written); the operation modes are the options of the existing hot water mode register (10005: `off` /
  `setpoint` / `offset` / `level`). The current temperature is the hot water temperature (10120). Every write is read
  back, like for the number and select entities. New key `water_heater_dhw`; no new registers. Enabled by default on
  new installations, disabled by default for entries that already had entities before this change (enable it in the
  entity settings). The Heat Pump Optimizer does not control hot water through this entity; do not let a planner and
  this entity write the same registers at the same time.
- Climate entity for the heating circuit (issue #19), in the *Heating* device. Target temperature writes the existing
  heating setpoint register (10001, 10 ... 70 °C in 0.5 K steps, out-of-range values are rejected before anything is
  written); *Off* / *Heat* write the existing heating mode register (10000: `off` / `setpoint`). The current
  temperature is the flow temperature. Every write is read back, like for the number and select entities. Other
  controller modes (offset, level) show as *Heat* and are listed in the `controller_mode` attribute. New key
  `climate_heating`; no new registers. Enabled by default on new installations, disabled by default for entries that
  already had entities before this change (enable it in the entity settings). Planners such as the Heat Pump Optimizer
  write the same registers: do not use both at once.
- Diagnostics download (issue #21) for bug reports: integration and Home Assistant version, selected equipment,
  capability flags, firmware and the last polled register values (raw and decoded) grouped by block. Host, MAC
  address and unique ID are redacted. It uses the data of the last poll, no extra Modbus reads.
- GitHub issue forms for bug reports and supported model reports (English), under `.github/ISSUE_TEMPLATE/`.
  Blank issues are disabled.
- Register reference `docs/registers.md` (issues #27, #3): a table of all registers with address, type, data type,
  scale, unit, range and status. Generated from the register map by `tools/gen_register_docs.py`; a test fails when the
  file is out of date. The status column reads from the register map and shows `open` until the map records sources.

### Changed
- CI runs the tests against the minimum Home Assistant version declared in `hacs.json` (2025.8.0) in addition to the
  newest ones. The minimum passes, so it stays at 2025.8.0.

## [0.6.0] – 2026-11-05

### Added
- **Automatic discovery via DHCP.** Heat pumps with a Luxtronik MAC prefix or the hostname `wp-novelan` are offered
  under *Discovered* – but only if the Smart Home Interface answers on Modbus/TCP (port 502, unit ID 1); other
